1What is optimization, and why power systems need it

Optimization is the art of making things as good as they can be — and the mathematics that makes "as good as they can be" a precise, computable statement rather than an opinion. A power system is a machine that must be operated and expanded through decisions taken every few minutes and every few years: which units to run, how to charge a battery, which line to reinforce, at what price to clear a market. Those decisions involve far too many interacting quantities, physical laws and technical limits for anyone to weigh by hand, and they must be justified afterwards — which is exactly what an optimization model provides.

Three questions hiding in one sentence

"Making things as good as they can be" only sounds vague until you unpack it. Each part of the sentence corresponds to one component of the model you will write:

Good?

Depends on what you want to achieve — cost, revenue, emissions, risk. This becomes the objective function.

Making?

Depends on what you can act upon and control. This becomes the decision variables.

Can be?

Depends on the limits on those possible actions — physical, technical, economic, regulatory. These become the constraints.

Optimization as a set of tools

Formally, optimization is a set of mathematical tools comprising two parts:

  • a modelling framework that translates real-world decision-making problems into a unified, structured mathematical form — an optimization model;
  • algorithms that compute optimal solutions to these models, either analytically or numerically.

The first part is a modelling skill and it is where most of the value — and most of the mistakes — live. The second is largely solved: efficient implementations already exist in commercial solvers. This course is about the first, using the second.

Where this shows up in the rest of the course:

Decision problem Typical objective, actions and limits Weeks
Economic dispatch and optimal power flow Serve demand at least cost, choosing production of each unit, within capacity limits and network flow limits 2

Every one of these is the same object with different content: an objective, some decision variables, some constraints. That is what makes the abstraction worth learning once.

2Anatomy of an optimization model

An optimization model translates a decision-making problem mathematically, expressing it in a standard form built from three components.

Decision variables

x = (x1, …, xN)T ∈ ℝN

The quantities the decision-maker can choose. They are defined as unknowns, and their optimal values are determined by the optimization algorithm — not by you.

Objective function

f : ℝN → ℝ

Evaluates the quality of any feasible solution — profit, cost, CO₂ emissions — which the algorithm then minimizes or maximizes, depending on the direction you choose.

Constraint functions

hj, gi : ℝN → ℝ

Reflect the limitations or requirements — operational limits, physical laws, logical relationships — that any feasible solution must satisfy, written as equality or inequality conditions.

The standard form

Put together, every model in this course can be written as:

minx ∈ ℝN
f(x)
s.t.
hj(x) = 0,∀j = 1, …, me
gi(x) ≤ 0,∀i = 1, …, mi

with me equality constraints and mi inequality constraints.

The feasible set

The constraints define the feasible set: the collection of all solutions x that satisfy every equality and inequality at once. The objective function then ranks the points inside that set, and an optimal solution is a feasible point whose objective value is at least as good as that of every other feasible point. Two consequences worth keeping in mind from the first week:

  • A model can be infeasible — the constraints contradict each other and the feasible set is empty. This is information about the problem, not a bug to be silenced.
  • A model can be unbounded — the objective improves forever inside the feasible set. In practice this almost always means a constraint is missing.
Conventions used throughout the course
  • Problems are written as minimization. Maximizing f is the same minimizing −f, and the optimal solution is the same.
  • Equalities are written as h(x) = 0 and inequalities as g(x) ≤ 0. Any "≥" or "≤ b" constraint can be rewritten in this form.
  • Write the model over sets and indices, never one line per unit or per hour. Define every symbol once, with its units and its domain.

3How an optimization model is solved

Optimization algorithms — solvers, or optimizers — find the best decision variables by exploring the feasible space, evaluating the objective function, and iteratively improving the solution. They are implemented efficiently in commercial software such as Gurobi and CPLEX, which is what you will call from your code from week 2 onwards.

Which algorithm applies depends on the class of the model you wrote — which is one reason the modelling choices matter well beyond aesthetics.

Model class Typical algorithm Idea in one line
Linear program (LP) Simplex algorithm Move along the edges of the feasible polytope until reaching an optimal vertex
Convex / non-convex non-linear program (NLP) Gradient descent and Newton methods Use first or second derivatives to take curvature-aware steps towards a stationary point
Convex / non-convex non-linear program (NLP) Interior point methods Follow an interior path defined by barrier functions and solve the resulting Newton system
Mixed-integer linear / non-linear program (MIP / MINLP) Branch-and-bound, branch-and-cut Split into subproblems and prune those whose relaxation cannot contain the integer optimum

Note: How these algorithms function is out of the scope of this course. But if you are interested, the following extensions dig deeper into it: Overview of optimization algorithms

4What this course does with all of that

What we will not do
  • Study the mathematics behind optimization algorithms
  • Implement optimization algorithms from scratch
  • Go deep into the computational complexity of solving different optimization models

These algorithms are already implemented efficiently in commercial solvers.

What we will do
  • Identify and formulate real-world decision-making problems in power systems as optimization models
  • Analyse the structure and properties of these models
  • Design validation scenarios and KPIs
  • Interpret results and communicate actionable insights

The aim is twofold: to equip you with optimization tools and model-based reasoning skills for complex decision problems, and to build the domain knowledge needed to identify, formulate, validate, solve and analyse those problems in modern power systems.

A two-way transformation

Creating value with optimization requires travelling in both directions: from messy real-world problems to structured mathematical representations, and back again — from abstract solutions to actionable real-world insights. A model that no one can act on has done only half the work.

The six steps you will practise

Every activity, example and assignment in the course supports one or more of these steps. They form a loop, not a list: the insights from step 6 usually send you back to step 1 with a better question.

  1. Identify the decision-making problem

    From unstructured narratives to decomposed and structured problem statements: who decides, what they want, what they control, what limits them.

  2. Develop the optimization model

    The modelling choices that lead to an abstract representation of the real-world problem — and the assumptions they carry.

  3. Validate the optimization model

    Insights and guarantees on the model's structure, its properties, and the characteristics of its optimal solutions.

  4. Design and run experiments

    Plan the scenarios and KPIs to evaluate, driven by the type of insight you are after.

  5. Analyse the results

    Look for patterns, trends and causal links between model inputs and outputs — why the results are what they are.

  6. Communicate insights and create value

    Close the loop, from abstract model solutions to actionable insights for the real-world problem.

This week covers steps 1 and 2 on a deliberately small example. Steps 3 to 6 arrive with duality, sensitivity analysis, experiments and storytelling later in the semester.

5Linear programs

A linear program is the special case where the objective and all constraint functions are linear and the decision variables are continuous. It is the workhorse of power system decision-making — economic dispatch, DC optimal power flow and market clearing are all LPs — and it is where the course starts.

Standard formulation

minx ∈ ℝN
z = N∑i = 1 ci xi
s.t.
N∑i = 1 Aji xi ≥ bj,∀j = 1, …, M
xi ≥ 0,∀i = 1, …, N
xi Decision variables, ∀i = 1, …, N — by convention non-negative. A free variable is modelled as xi = xi+ − xi− with xi+ ≥ 0 and xi− ≥ 0.
ci Cost parameters, ∀i = 1, …, N. The objective is minimized by convention.
Aji, bj Left-hand-side and right-hand-side constraint parameters, ∀i = 1, …, N and ∀j = 1, …, M. The linear constraints describe the feasible space.

Matrix formulation

Collecting variables, costs and constraints into vectors and a matrix gives the compact form used in most textbooks and in solver documentation:

minx ∈ ℝN
z = cTx
s.t.
Ax ≥ b
x ≥ 0

with x, c ∈ ℝN the vectors of decision variables and costs, b ∈ ℝM the right-hand-side vector, and A ∈ ℝM×N the left-hand-side constraint matrix — one row per constraint, one column per decision variable.

Why the LP case deserves the attention

LPs are solved reliably at very large scale, an optimal solution can always be found at a vertex of the feasible polytope, and every constraint carries a dual variable — the value of relaxing it by one unit. In a dispatch model that dual is the electricity price. The whole of weeks 4 to 6 rests on this.

6Worked example — the night bike lane cleaning problem

The example deliberately contains no electricity at all. Its structure, however, is exactly that of the economic dispatch problem you will build next week — which is the point.

The problem statement, as given

The municipality must clean snow from its bike lanes. The lanes are spread over several districts, and the total length must be cleaned before 6 am.

The municipality does not want to pay for cleaning more than what is needed.

It owns no machines, so the work is bought from a number of contractors.

Each contractor charges a fixed price per kilometre and clears at its own speed, so none of them can clean more than a certain length — depending on its speed and the remaining hours before the deadline.

Step 1 — Identify the decision-making problem

Step 1 requires a thorough understanding of the decision-makers, how they behave and how they interact. Here there is a single decision-maker — the municipality. The contractors are described only by a price and a speed, so they are taken as given: this first model does not represent them as strategic players. Three questions turn the narrative into a structured problem statement.

Question Answer, in the words of the narrative Becomes
What objective does the decision-maker want to achieve? Pay as little as possible, and not for more cleaning than is needed. Minimize the total amount paid to the contractors — the objective function.
What actions can it take? It owns no machines, so its only lever is how much work it buys from each contractor. The number of kilometres allocated to each contractor — the decision variables.
Are there restrictions on the feasible actions? The whole network must be cleared before 6 am, and no contractor can clear more than its speed allows in the hours that remain. One requirement on the total work done and one capacity limit per contractor — the constraints.

The structured problem statement, in one sentence: choose how many kilometres of bike lane to buy from each contractor so that the full length of the network is cleared before the deadline, at the lowest possible total cost.

Step 2 — Develop the optimization model

Step 2 turns that sentence into mathematics. It starts, always, with notation: every set, parameter and variable defined once, with its units.

Symbol Meaning Unit Role
N Number of available contractors — Set size
D Number of districts to be cleared — Set size
H Hours available before the 6 am deadline h Parameter
ci Price of contractor i = 1, …, N DKK/km Parameter
vi Clearing speed of contractor i = 1, …, N km/h Parameter
Lj Length of bike lane in district j = 1, …, D km Parameter
xi Kilometres cleared by contractor i = 1, …, N km Decision variable
Remember this one

The parameter H converts a clearing speed (in km/h) into a maximum workload (in km). It plays exactly the same role as a time step Δt does when converting a power (in MW) into an energy (in MWh) in the power system models you will meet later in the course.

The modelling choices behind the formulation

Before writing a single equation, notice what has been decided. Each of these is a choice, defensible here and worth revisiting when the problem changes:

  • Work is continuous and divisible. Kilometres can be split arbitrarily between contractors, so the variables are continuous and the model stays an LP. Whole-street assignment would need integer variables.
  • Contractors work in parallel over the same H hours, with no travel or set-up time between districts.
  • Price is linear in distance, with no fixed call-out fee — hence a linear objective. A call-out fee would introduce a binary variable per contractor.
  • Districts enter only through the total length. The model tracks how much is cleared, not where; the spatial detail of Lj is aggregated away. This is the strongest simplification in the model, and the natural first thing to relax.
  • Exactly the required length is cleared, which is how "does not want to pay for cleaning more than what is needed" is expressed — an equality rather than a "≥".
  • All prices, speeds and lengths are known when the decision is taken. The problem is deterministic; uncertainty arrives in week 8.

The resulting linear program

minxi
N∑i = 1 ci xi
(1)
s.t.
0 ≤ xi ≤ vi H∀i ∈ {1, …, N}
(2)
N∑i = 1 xi = D∑j = 1 Lj
(3)

Reading the model back in words

(1) Objective. The total bill is the sum, over contractors, of a price per kilometre times the kilometres bought. It is linear in x, and it is the only place where ci appears.
(2) Capacity limits. A contractor cannot clear a negative length, and cannot clear more than its speed allows in the hours remaining: vi H is a maximum workload in km. One such pair of bounds exists per contractor.
(3) Balance. What is bought equals what is needed: the kilometres cleared across all contractors equal the total length of bike lane across all districts. This single equality is what couples the contractors to each other.

The model is a linear program with N continuous variables, one equality constraint and N pairs of bounds. Mapping it onto the matrix form of section 5: c is the vector of prices, x the vector of workloads, and the balance constraint is a single row of A filled with ones.

What the feasible set and the optimum look like

With two contractors the whole model fits in a plane, which is worth drawing once. The bounds (2) give a rectangle; the balance constraint (3) cuts a straight segment across it; the cost contours are parallel lines whose slope is set by the price ratio. The optimum sits at an endpoint of the segment — a vertex — unless the two prices are exactly equal.

Two contractors, contractor 1 cheaper than contractor 2. The dashed rectangle is the set of workloads allowed by (2); the solid red segment is the feasible set once (3) is imposed; the optimum is the endpoint where the cheaper contractor is loaded to capacity.

The same reasoning generalises to any N: rank the contractors from cheapest to most expensive, load each to its maximum vi H until the required length is met, and leave the rest idle. Exactly one contractor is normally partially loaded, and its price is what one extra kilometre of bike lane would cost the municipality. That ordering is a merit order, that last contractor is the marginal one, and its price is the dual variable of constraint (3) — three concepts you will meet again in weeks 2 and 5, with generators instead of snow ploughs.

When is the model infeasible?

If the total capacity available before the deadline is smaller than the length to be cleared — that is, if Σi vi H < Σj Lj — no allocation satisfies (2) and (3) at once and the solver returns "infeasible". That is a genuine answer to a genuine question, and the modelling response is to change the problem: hire more contractors, move the deadline, or allow part of the network to stay uncleaned at a penalty. The last option is the same device as load shedding in a dispatch model.

From bike lanes to power systems

Rename the symbols and the very same LP becomes next week's single-hour economic dispatch:

And then steps 3 to 6

The model is written, which is where week 1 stops — but not where the work stops. Validate it: check that the bounds hold, that the balance is met to solver tolerance, and that limiting cases behave (one contractor with unlimited capacity should take everything; equal prices should make the allocation indifferent). Experiment: what happens as the deadline moves earlier and H shrinks, or when a cheap but slow contractor is added? Analyse: which constraints bind, and which contractor sets the marginal price? Communicate: what should the municipality actually do differently tomorrow night? Those four steps are the substance of the rest of the course, and of both assignments.

7Takeaways

  1. An optimization model has exactly three components — decision variables, an objective function, and constraints. Naming them correctly is most of the modelling work.

  2. The constraints define the feasible set; the objective ranks the points inside it. Infeasibility and unboundedness are results, and both usually say something true about the problem statement.

  3. The class of the model — LP, NLP, MIP — follows from your modelling choices and determines which algorithm the solver uses. You will not implement those algorithms; you will be responsible for the model they are given.

  4. A parameter that converts a rate into a quantity — H here, Δt in every power system model to come — is where units get lost. Check them every time.

  5. A bike lane cleaning problem and an economic dispatch are the same linear program with different nouns. Recognising structure across problems is the transferable skill this course is built on.

AAppendix — Units in the DC power flow: the per-unit system and the voltage angles

The DC power-flow equation of Week 2 can be written in physical units, in per unit, or — as in the lecture example and Exercise 2 — with powers in kilowatts and reactances in per unit. The equation looks the same in all three; the angle variable does not mean the same thing. This appendix states the units of every quantity in each convention and shows how to convert the voltage angles returned by a DC-OPF model to radians, which is what the small-angle assumption (assumption #4 of the linearisation) is about.

A.1 Why a per-unit system?

A power system spans several voltage levels connected by transformers, and its physical quantities range over many orders of magnitude — volts to hundreds of kilovolts, watts to gigawatts. Expressing every quantity relative to a base, a fixed reference value of the same kind, removes the transformer ratios from the equations, brings all voltages close to one, and keeps all numbers within a narrow range. Two bases define a per-unit (p.u.) system:

  • a base power Sb, common to the whole system — 100 MVA is the usual choice in transmission studies; for the small example of the Week 2 lecture and of Exercise 2 we use Sb = 100 kW;
  • a base voltage Vb for each voltage level, the levels being linked by the transformer ratios.

The other bases follow from these two: the base impedance is Zb = Vb2/Sb and the base current Ib = Sb/(√3 Vb) in a three-phase system. A quantity in per unit is its physical value divided by the corresponding base. Angles are not divided by anything: they are dimensionless already and stay in radians.

Quantity Physical value (unit) Base Per-unit value
active power P (W) Sb p = P/Sb
voltage magnitude V (V) Vb v = V/Vb
line reactance X (Ω) Zb = Vb2/Sb x = X/Zb = X Sb/Vb2
susceptance B = 1/X (S) 1/Zb b = 1/x

A.2 The DC flow equation in physical units

For a lossless line between nodes i and j, the active power leaving i towards j is

Pij = Vi VjXij sin(δi − δj),[W] = [V] [V] / [Ω]
(A1)

written with three-phase power and line-to-line voltages, or equivalently per phase with phase voltages. The dimension check holds because V2/Ω = W; the sine is dimensionless. Note that the small-angle step of the DC approximation, sin(δi − δj) ≈ δi − δj, is only valid for angles in radians — in degrees it would be off by a factor π/180. With a flat voltage profile (Vi = Vj = V, assumption #2) and small angle differences (assumption #4),

Pij ≈ V2Xij (δi − δj),P in W, V in V, X in Ω, δ in rad
(A2)

A.3 The same equation in per unit

Dividing (A1) by Sb and substituting Vi = vi Vb and Xij = xij Zb = xij Vb2/Sb, the bases cancel:

pij = vi vjxij sin(δi − δj),all quantities in p.u., δ in rad
with vi = vj = 1 and small angles:pij = 1xij (δi − δj) = bij (δi − δj)
(A3)

This is the form used in the Week 2 lecture and notes: every symbol is dimensionless except δ, which is in radians. A whole DC-OPF can be written in per unit by dividing loads, capacities and flow limits by Sb; the objective then needs the cost coefficients in DKK per p.u.-hour, cgG Sb, if it is to remain in DKK.

A.4 Mixed units — the lecture example and Exercise 2

The lecture example and Exercise 2 keep the powers in their physical unit (kW) but give the reactances in per unit. The model then solves

Pij [kW] = 1xij (δ~i − δ~j),
(A4)

where δ~i is whatever number the solver returns for the angle variable. Multiplying (A3) by Sb gives Pij = (1/xij) (Sbδi − Sbδj); comparing with (A4) identifies the model's angle.

Key equation
δ~i = Sb δi⟺δi [rad] = δ~iSb,δi [°] = 180π δ~iSb

with Sb expressed in the unit of the flows (here kW). The angle variable of a model with powers in kW and reactances in p.u. is a voltage angle in radians multiplied by the base power; it carries the unit of the flows and cannot be interpreted until Sb is known.

Three consequences follow.

  1. Nothing else changes

    The substitution δ~ = Sb δ is a change of variable: the balance equations, the flow limits and the reference condition δref = 0 are all linear and homogeneous in δ, so the set of feasible dispatches, the optimal dispatch, the flows and the cost are identical for any Sb > 0. This is why the base can be left unstated without altering a single result — except the angles.

  2. Assumption #4 can only be checked after converting

    Whether the angle differences are "small" depends on Sb: the same model with reactances given on a 1 MW base returns angles ten times smaller than on a 100 kW base. The base therefore belongs with the data.

  3. Reactances in ohms shift the scaling to the voltage

    Comparing (A2) with a model in W and Ω — the other option mentioned on the DC-OPF slide — gives δ~i = V2 δi, so the conversion needs the voltage magnitude instead of the base power (δi = 103 δ~i/V2 if the flows are in kW and V in volts).

A.5 Worked example: the 3-bus system of the Week 2 lecture

Data of Exercise 2: x12 = x13 = 0.1 p.u., x23 = 0.5 p.u. on Sb = 100 kW; line limits 75, 150 and 150 kW; load 200 kW at n3. The base-case DC-OPF gives the dispatch (75, 120, 5) kW, the flows p21 = 75, p13 = 150, p23 = 45 kW, and the angles δ~ = (0, 7.5, −15) in the model's unit. Converting with Sb = 100 kW:

The same example entirely in per unit

With Sb = 100 kW: load L3 = 2.0; generator capacities 1.5; line limits 0.75, 1.5, 1.5; reactances unchanged; cost coefficients cgG Sb = 7000, 1500, 15000 DKK per p.u.-hour. The optimal dispatch is (0.75, 1.2, 0.05) p.u., the angles are (0, 0.075, −0.15) rad directly, and the cost is again 7800 DKK.

A.6 Practical rules

  • State the base with the data. A reactance "in p.u." is meaningless without Sb (and Vb, if ohmic values are ever needed). In code, make Sb an attribute of the input data, next to the reactances it refers to.
  • One convention per model. Either everything in per unit (angles in radians, costs in DKK per p.u.-hour), or physical powers with per-unit reactances and a conversion δ = δ~/Sb when the angles are reported. Never mix the two within one model, and never compare angles across models built on different bases or with reactances in different units.
  • Two sanity checks. Dimensions: the right-hand side of the flow equation must have the unit of the flow. Small angles: after conversion, max |δi − δj| should be well below π/6, and sin(δi − δj) close to δi − δj; if not, the DC approximation is being used outside its domain of validity.

This is the same device as the parameter H of the bike-lane example and the time step Δt of the dispatch models (takeaway 4): a factor that converts one kind of quantity into another, and the place where units are most easily lost.
